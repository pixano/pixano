# Pixano — Backend Processing Architecture

**Status:** Living document — records what is decided, by subject. Not a full specification of the subsystem. Step 1 is delivered and reviewed; [the review](../reviews/etape1-revue.md) keeps the findings, this document keeps the decisions.
**Scope:** the batch processing subsystem: running pre-annotation, statistics and indexing jobs over a whole dataset, in the background, while annotation continues in the interface.
**Provenance:** the accepted plan is `pixano-plan-developpement-backend`, which defines six steps. This document records the decisions taken while implementing them, so that later work builds on them instead of reopening them. A decision is written where its subject lives, not in the order it was taken.

---

## 1. Vocabulary

Aligned with the conventions of the ecosystem (Celery, Airflow, Dagster):

- A **task** is the processing of one atomic unit — an image, a text, or a whole video for tracking.
- A **job** is the execution of one kind of processing over a dataset: N tasks executed in batches.
- A **chunk** is one batch of tasks: the unit a worker claims and completes.
- A **workflow** is a chain of jobs. Out of scope until step 5.

## 2. Execution model

Jobs run in `pixano-worker`, a service of its own, never in the API process — a job over 50 000 images must not degrade the latency of the annotation interface.

**The worker shares nothing with the API but PostgreSQL and the storage.** No process, no memory, no local filesystem handoff. This is what allows the worker to run on another machine, which is the normal situation outside local mode.

**Media never travel through Pixano.** The inference server is handed paths, or presigned URLs, never bytes. Each side declares the root under which it sees the storage, and the worker translates between them before a call. That pair covers only the case where both sides can read the same storage; a dataset in object storage, or one that stays on its owner's machine, are other strategies of the media resolver.

**Writes are idempotent.** A worker that dies mid-chunk re-runs that chunk on restart, so processing a chunk twice must produce the same result. Results go to LanceDB while the chunk's completion is recorded in PostgreSQL — two stores, so the two writes cannot share a transaction, and delivery is at-least-once by construction.

## 3. What PostgreSQL carries

Three roles, from the start:

1. **The queue.** The chunk table is the queue; a pending chunk is a row a worker claims with `SELECT … FOR UPDATE SKIP LOCKED`.
2. **The execution state.** Recovery after an outage needs no replay at startup: the pending work is already in the database.
3. **The progress events.** Emitted with `LISTEN/NOTIFY`, relayed to the interface over SSE.

The application records a job request; the worker splits it, inserting its chunks and its total in one transaction, so a job is never seen with half its work.

## 4. The schema

Lives in a dedicated PostgreSQL schema, `pixano_jobs`, so that the accounts and access rights of step 6 do not share a namespace with the queue. Installed by the worker — the only component with a PostgreSQL driver — from `packages/pixano-worker/src/pixano_worker/sql/schema.sql`.

### 4.1 Tables

| Table        | Holds                                                                                                                                                                   |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jobs`       | one row per submitted job: its kind, its dataset, its validated parameters, its state, its task counters, and the lease of the worker splitting it                      |
| `job_chunks` | the queue: one row per batch of tasks, with its lease, its attempt count, when it may next be claimed, and — once done — how many of its tasks were produced or skipped; plus, for a kind that finalizes, the job's final chunk (§8.5) |
| `job_items`  | the quarantine: one row per item a kind could not process, with the reason                                                                                              |
| `job_events` | the append-only progress log an interface replays when it reconnects                                                                                                    |

Job identifiers are `uuid` generated by the database, so neither the application nor the worker needs an identifier library to create a job. Chunk and event identifiers are `bigint identity`: the claim index will carry millions of entries, and increasing identifiers give it locality and a natural FIFO order.

Timestamps are `timestamptz` and are **produced by the database clock**, never by a worker. A worker with a skewed clock must not be able to over-hold or steal a lease.

Payloads are `jsonb` with a `jsonb_typeof(...) = 'object'` check, so a pydantic model always fits and no column can hold a bare scalar.

### 4.2 Two flaws ruled out by constraints

The existing SQLite import/export store (`src/pixano/datasets/io/jobs.py`) has two defects this schema makes structurally impossible rather than merely discouraged:

- **Cancellation stashed in the error payload.** `request_cancel` writes `{"cancel_requested": True}` into `error_json`, overwriting any previous error and being overwritten in turn. Here cancellation has its own column, and `CHECK (error IS NULL OR state = 'error')` forbids the alternative.
- **Liveness by PID.** `mark_interrupted_on_boot` decides a job is dead with `os.kill(pid, 0)`, which is meaningless as soon as the process is on another machine, and vulnerable to PID reuse. Here a chunk carries a **lease with an expiry**: a chunk whose lease ran out becomes claimable again, with no boot hook and no state to invent. `CHECK ((state = 'running') = (lease_until IS NOT NULL))` forbids a chunk that keeps a stale lease or that runs without one.

The `interrupted` state of the SQLite store has no equivalent here, for that reason: the system repairs itself.

### 4.3 Indexes

Each index serves one named query. The claim index is **partial** — it carries only claimable chunks, so it shrinks as work advances while the table keeps everything, and a chunk leaves the index the moment it is claimed. Its key is the chunk identifier, exactly the `ORDER BY` of the claim, so `SKIP LOCKED` walks forward instead of re-sorting.

The expired-lease sweep is a separate statement, deliberately: folding it into the claim (`state = 'pending' OR (state = 'running' AND lease_until < now())`) would make the partial index unusable.

A partial unique index on `job_id WHERE final` keeps one final chunk per job at most, and lets releasing it, and saying that a job is finalizing, find it without a scan of the job's chunks (§8.5).

### 4.4 Chunk payloads are opaque

A chunk carries a `jsonb` payload the job kind interprets, not a fixed range of identifiers. Pixano tasks are not integers — an image is a shortuuid in a LanceDB table — LanceDB row order is not a contract, and the most useful job is a selection ("run this model on the 240 images I ticked"), which has no range at all. Keeping the payload opaque is what lets video tracking and embeddings share one queue without the engine knowing their shape, which is the condition for job kinds to stay plugins. `task_count` stays a real column: progress is a concern of the engine, which must never look inside a plugin's payload to draw a progress bar.

## 5. Schema changes: wipe and recreate

**There is deliberately no migration engine.** Until this database holds something irreplaceable — the user accounts of step 6 — wiping and recreating _is_ the migration strategy: jobs are disposable, and their results live in LanceDB, not here.

What the version marker buys is that the failure is loud. `CREATE TABLE IF NOT EXISTS` creates a missing table but never alters an existing one, so a changed schema would otherwise leave a worker running against tables that are no longer its own, breaking later and far from the cause. Instead the worker compares the version recorded in the database with the one the code expects, and on a mismatch refuses to start with the command to run.

**Any change to the DDL of `schema.sql` must increment `SCHEMA_VERSION`.** A change to its comments alone does not: it changes nothing in the database.

When this database does hold something irreplaceable, a real runner is added by _baseline_: a first migration containing the schema as it then stands, marked already-applied on existing databases and executed on new ones. That retrofit is cheap, which is what makes deferring it safe.

## 6. The queue is home-grown — decided, not to be reopened

Procrastinate was evaluated against this schema (version 3.9, a timeboxed spike). It is a
capable library and offers, ready-made, the one thing we hand-roll: recovery of jobs left
behind by a dead worker, through worker registration, heartbeats and a stall sweep. It also
brings `LISTEN/NOTIFY`, retry strategies, and batch enqueuing.

It was **not** adopted, for one structural reason and two practical ones:

- **It owns the worker loop.** Step 4 requires a cap on in-flight calls _per model_, derived
  from the replicas of the inference deployment: a worker claims a chunk only when a slot is
  free. That is a pull policy gated by a per-model semaphore; Procrastinate exposes a global
  concurrency setting. We would be fighting its loop exactly when step 4 becomes the subject.
- **It does not replace our schema, it adds to it.** Four tables, three SQL types, 20 kB of
  DDL — and our `jobs` table would still be needed, since Procrastinate has no notion of a
  user-facing job made of N chunks with a progress bar. Two job models, two state
  vocabularies to map.
- **It fetches one job at a time.** Mapping one Procrastinate job to one of our chunks makes
  that acceptable, but it forfeits the batch claim we already have and measured.

Partial adoption is not on the table: the stall machinery is tied to its own tables and job
lifecycle. The cost we accept in exchange is owning the recovery of abandoned work.

**Two lessons taken from reading its queries:**

- Its heartbeat is **per worker**, not per unit of work: one row refreshed per worker per
  interval, whatever it holds. Our per-chunk lease refreshes one row per in-flight chunk.
  Negligible with one or two workers; worth revisiting if workers ever number in the dozens.
- It runs a **second, independent stall detector** — work whose start event is older than a
  threshold, regardless of heartbeat. The gap it closes is ours too: a live worker that keeps
  beating while one chunk hangs — blocked in an inference call that never returns — would
  hold that chunk forever. The docker probe catches a dead worker, not a healthy worker with
  dead work. Hence the maximum chunk duration, independent of the lease (§9).

## 7. The worker depends on `pixano` — decided on measurement

The worker must write its results into LanceDB with the Pixano schemas, which raised the
question of whether it should depend on the `pixano` package, on a set of optional extras, or
on a shared package extracted for the purpose. The worry was that depending on `pixano` would
drag the whole web application into the worker image to write a vector.

Measurement settles it:

|                                      |                                    |
| ------------------------------------ | ---------------------------------- |
| `pixano.schemas` loads               | 22 distributions                   |
| `pixano.datasets.dataset` loads      | 25 distributions                   |
| `pixano.api.main` loads              | 67 distributions                   |
| `pixano` runtime closure on disk     | **647 MB** across 89 distributions |
| The dataset layer alone              | **600 MB** across 29 distributions |
| **What a shared package would save** | **47 MB — 7 %**                    |

The web layer genuinely is not imported by the dataset layer. But the weight is not there: it
is in polars (145 MB), opencv (119 MB), pyarrow (115 MB), lancedb (99 MB), pandas and duckdb —
the dependencies of LanceDB itself, which the worker needs whatever we do. Extracting a third
package to publish, version and keep in step, for 7 %, is not a good trade; optional extras
would buy the same 7 % for the same carving.

**So the worker depends on `pixano`.**

**A better lever, noted and not taken:** `pixano/features/utils/image.py` imports cv2 at module
level, and that file is imported by `schemas/views/image.py` — so opencv, 119 MB, is pulled
into `pixano.schemas`. cv2 is used there by three functions (reading a depth image, applying a
colour map, extracting mask contours). Making that import lazy would save more than twice what
the whole shared-package exercise would, for a one-file change, and it would benefit every
consumer rather than only the worker. It touches the core, so it deserves its own change and
its own verification that nothing relies on the import's side effect.

## 8. Failures and quarantine

### 8.1 Three families

| Family        | Example                                          | Handling                                                                                                |
| ------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| **Transient** | inference unreachable, restarting, answering 503 | the chunk goes back to the queue after 15 s, doubling each time up to 5 min; set aside after 5 attempts |
| **Item**      | a corrupt image, a missing file                  | the chunk finishes; the item goes to `job_items` with its reason                                        |
| **Fatal**     | a miscounting kind, an unknown model             | the chunk fails, and the job with it                                                                    |

**Why a delay.** Handing a chunk straight back would claim it again a moment later, against an inference that is still restarting, and burn every attempt before it returns. `available_at` makes a chunk invisible to the claim until then.

**Why five attempts.** With that delay, they leave close to four minutes for an inference to come back — a restart with a model reload. Measured on the local stack: a 45-second outage plus the restart used four of the five. A longer outage sets the affected chunks aside and fails the job; a deployment whose inference restarts more slowly should raise the number. Validated in review together with the retry: five attempts are acceptable because a failed job is not a dead end.

**A job that ended badly can be run again.** `POST /jobs/{id}/retry` reopens the chunks in error or cancelled, clears the job's error and its cancellation request, and puts it back to `pending` — or to `planning` when it never got chunks, since planning again is the only way to get some. Refused with 409 for a job in any other state; the state event is written in the same transaction. Completed chunks keep their results, and the reopened ones get their attempts back without `attempts` ever going down, since it is the fencing token: `attempts_floor` records where the count restarts (schema version 5). A button in the panel is deferred.

**Both recovery paths cap attempts and settle the job.** Expired leases and a restarted worker taking its own chunks back count against the same five; a chunk set aside settles its job. A job whose last chunk was abandoned used to stay running forever, and a chunk that crashed its worker looped for good once restarts were automatic.

### 8.2 An item is blamed only on an answer

The inference answers `500 internal_error` for a corrupt image, a missing path and a path outside its roots alike, and refuses the whole batch as soon as one image in it is bad. The embeddings kind therefore splits a refused batch in two until the images that fail on their own are isolated — seven calls instead of one for a chunk of eight with one bad image, and only on that day. **The bisection is temporary**: the fix belongs in pixano-inference (a 4xx, and a per-image answer), and goes away with it.

A failure **without** a response — status 0 from the client, which is how it wraps a connection error — makes the whole chunk transient, even halfway through that search. The first version did not know about status 0 and quarantined seven healthy images during an inference restart; the scenario of §15 caught it.

**When every image of a chunk is refused, the inference itself is asked whether it is at fault.** A small generated image is sent as bytes. Refused, the server is unwell and the chunk is transient. Accepted, the images are to blame — unless they were sent by path: the server may be unable to read the media storage it was told to mount, and refuse every path through no fault of the images, so one of them is sent again as bytes; if it passes, the chunk is retried with that reason instead of hundreds of sound images going to quarantine. A first version presumed an outage from two refused images up, which made the decision hang on the size of the batch, and the last chunk of a dataset often holds one image.

**What is resent, and what is not.** The media resolver says how it designated each medium (`ResolvedMedia.designation`: `path`, `url` or `bytes`), and the check follows it. A medium designated by path is resent as the bytes this worker reads from its file (`reader.open_media`), not from the dataset, which holds no bytes for a view designated by path — a view carries a `uri` or `raw_bytes`, never both: resent from the dataset, the check would find nothing and the whole chunk would go to quarantine, on every real dataset, while tests whose doubles return bytes for any view would pass. The file is read only if it is under this worker's media root once links are followed: the check compares real paths (`os.path.realpath`), the root's included, so a link under the root to a file outside it is not read, and its medium goes to quarantine like any other refused path. A file this worker cannot read either decides nothing: the next medium sent by path is tried, and when this worker reads none of them, the media go to quarantine; a silence at that second call is an outage, and the chunk is transient; an error no medium causes there — a denied access, an answer this worker cannot read — fails the chunk, as it does on the kind's own call. The reason names the inference's media root and the variables to check — `PIXANO_INFERENCE_MEDIA_ROOT` on the worker, `PIXANO_INFERENCE_MEDIA_ROOTS` on the inference — as the resolver states it, beside its path designation. **A medium designated by URL is not checked that way**: the bytes this worker could send say nothing of whether the inference reaches the URL's source. Refused with the rest of its chunk, it goes to quarantine; whether to quarantine it or to retry the chunk with a reason is still open, and the code quarantines it. Step 3, which adds sources reached by URL, diagnoses each source in its own way (§20).

### 8.3 Skipped is not quarantined

A task the calculation does not apply to is counted, not stored — the embeddings kind plans existing media only and skips nothing, but a kind that plans by record still may. Otherwise a lidar dataset would fill the quarantine with 26 362 rows that are not errors. A kind's outcome is `produced + skipped + quarantined`, and must total the chunk's `task_count`; a kind that miscounts is a fatal failure.

### 8.4 What a job says when it ends

**The outcome is aggregated on read** from the chunks and the quarantine, and shown by the API and the panel once a job ends. It is not kept as counters on the job: a counter can drift from what it summarises. `done_tasks` is the one denormalised counter, kept to avoid summing chunks on every progress event; it shares a transaction with the chunk it counts, and a concurrency test compares it against the sum. Validated in review.

**A failed job says why.** The API exposes the job's error, or its first failed chunk's, without the stack trace; the panel shows the reason. The worker's reasons are in English for that purpose, as is the whole worker.

### 8.5 A job's closing step: the final chunk

Some work only makes sense once a job's chunks are all done — an index trained on every vector the job wrote, figures over every row. No chunk can do it, and the last chunk to finish does not know it is the last. A kind that overrides `finalize` (writing-a-job-kind.md §1) gets a **final chunk**: recorded at planning with the others, last in rank, with no task (`task_count = 0`, the only chunk allowed none), in the state `waiting`, which no claim reads.

**Released by whoever settles the job.** Settling a job now first tries to release its final chunk, in the same transaction (`queue.RELEASE_FINAL`): when no other chunk of the job is left undone — none pending, running, failed or cancelled — and the job is neither cancelled nor finished, the chunk becomes `pending`, a state event `{"state": "running", "finalizing": true}` is written, and the job is not settled. The job settles once the final chunk is done, failed or cancelled.

**A settlement locks the job's row first** (`runner.LOCK_JOB_FOR_SETTLEMENT`), as `finish` locks it to count a chunk done. Read committed, each statement sees what committed before it: without the lock, the last two chunks of a job finishing together could have one's settlement check the release while the other still ran, then settle the job once that other had committed — `done`, without its closing step, which stayed waiting for good. Under the lock no chunk is counted done between the two reads, so the last chunk to finish sees the others done; two settlements meeting are serialised by it, and the second finds the final chunk no longer waiting. The events that announce a job finalizing — the release's, the start of a retried job whose closing step alone was reopened — carry `"finalizing": true`, and any other state event of the job clears it.

**The recovery pass settles the jobs nothing else will** (`runner.settle_stranded`, beside the expired leases, every 30 s): a job in flight none of whose chunks is pending or running. A worker that died between a chunk's result and the settlement that follows it leaves one — a job running for good, whether or not its kind has a closing step; so does a retry with nothing to reopen. The pass settles it as a chunk would, releasing its final chunk if its work is done.

**It is a chunk, so it inherits everything a chunk has**, without a second copy of each: the claim, the lease and its recovery, the attempts and the fencing token, the time limit, the delay after a transient failure, the cancellation, `POST /jobs/{id}/retry`. Rather than a step the last chunk would run, which would need all of them again. It runs `finalize` in a thread, under the worker's write lock of the dataset, on the dataset reopened outside the cache, since it must see what every worker wrote. A `DatasetBusyError` — someone else writing the dataset — hands it back as transient: the chunks are all done, and the job must not lose them for a person's save. A chunk that met the same error fails (§12); a final chunk is the one place where waiting costs nothing but time.

**It never runs after a failure or a cancellation.** A job with a failed chunk settles in `error` with its final chunk still waiting; a cancelled one settles `cancelled` the same way. A retry reopens the failed chunks and leaves the final chunk waiting — the application's statements did not change, since they only reopen chunks in error or cancelled — and the closing step runs once the reopened chunks pass. A job cancelled while its last chunks ran has nothing to reopen: its work all completed, its final chunk waits, and after a retry the recovery pass releases it. A cancellation after the release takes the final chunk out of the queue with the job's other pending chunks; a retry puts it back. One that arrives while the final chunk runs lets it complete — nothing is interrupted mid-chunk — and the job reads `cancelled`; its closing step did run.

**It counts no task.** The job's total, its progress and its outcome are those of its work: the final chunk is done with nothing produced and nothing skipped, and advances no counter. The job reads `running` until it ends — `pending`, after a retry, until its final chunk is claimed.

Schema version 6 added the final chunk: the `final` column, the `waiting` state, the two constraints that only a final chunk waits and that a chunk has tasks exactly when it is not final, and the partial unique index of §4.3. As for every change of the schema (§5), a database at version 5 is refused at startup, and the queue is recreated empty.

## 9. The worker process

The worker loop runs on asyncio, as the plan asks; the job-kind contract stays synchronous and runs in threads, since LanceDB blocks whatever we do.

| Setting                         | Default | Why                                                                                           |
| ------------------------------- | ------: | --------------------------------------------------------------------------------------------- |
| `PIXANO_WORKER_CONCURRENCY`     |       4 | a cautious starting point, **not measured**; see below                                        |
| `PIXANO_WORKER_CHUNK_TIMEOUT_S` |    1800 | above the embeddings kind's usual worst case — one call and its retries, about twenty minutes |

**Concurrency is coupled to two things it does not own.** The inference server has its own limit on simultaneous requests, which the worker shares with every other client: four chunks in flight are four requests competing for it. And each call carries its own timeout and retries, so a slow server multiplies into the chunk time limit. The default stays at four, validated in review; on the CPU stack, throughput already fell as batches grew (§14), and whether four chunks in flight help or hurt there is unknown.

- The worker **never claims more chunks than it has free slots**: a claimed chunk's lease is already running.
- **The lease is refreshed** three times per lease while a chunk runs. A refresh that meets a database outage is logged and retried at the next interval, never filed as the chunk's failure.
- **A chunk over its time limit is sent back.** Its thread cannot be stopped; if it ever completes, the fencing token refuses its result and its idempotent write doubled nothing. The limit is a deployment setting today, and a slow inference answering 500 on a corrupt image can push a legitimate bisection past it. Decided in review: the limit should follow the work — a kind declares a weight per chunk at planning. Measure first; designed with the chunk work of §19.
- **The heartbeat is its own task.** It used to beat once per loop turn, so any chunk longer than the probe's window made docker declare a working worker dead.
- **A full worker still reclaims expired leases**, on the reclaim interval, instead of waiting for one of its own chunks to finish.

**Stuck threads are abandoned, not the worker.** Job code runs in a bounded pool that counts threads still busy after their chunk timed out or was abandoned at shutdown. When as many are stuck as there are chunks in flight, the pool is renewed in place — a fresh executor, the old threads left to finish on their own — and the loop goes on. A first version exited the process and relied on the restart policy; checked against Docker, `on-failure:N` never resets its count after a healthy run, so that worker would have stayed down for good at its N-th incident. Renewing frees no lock: a thread stuck in a dataset's write keeps that dataset's write lock, which lives outside the pool, until the process ends. Every wait for that lock is bounded, so that no chunk waits on it for good; while they wait, that dataset's chunks still take the worker's slots (§12, §18).

**The worker survives its database.** A PostgreSQL restart used to kill it for good — checked on the running stack. The loop waits with a short capped backoff, as startup does; the pool checks a connection before lending it, and gives up a borrow after five seconds so that a stop during an outage is not held for the default thirty. A database error raised anywhere around a chunk propagates and leaves the chunk to its lease.

**An unexpected exception in a loop turn is logged and survived**, with a one-second pause, counted, and traced once every sixty repeats: killing the worker made nothing more visible than its trace. Sixty consecutive failures — a minute — end the process: the chunks in flight get their grace and are handed back as on any stop, and the exit code is 1 so that the restart policy brings up a fresh one. A defect that does not pass in a minute will not pass in an hour.

**SIGTERM stops the worker gracefully.** It stops claiming, gives chunks in flight 30 s, hands back what still runs, and exits; the compose allows 45 s. As the container's process 1 without a handler, it used to ignore SIGTERM until docker killed it.

**The restart policy is `unless-stopped`.** It was `on-failure:3`, chosen so that a worker refusing an incompatible schema stays down with its message; that misread the decision of §5, which was to refuse to start with a clear message, not to stay down for good — and Docker never resets the count after a healthy run, so the third incident of a long life left the worker down. A crash loop on a stale schema is accepted: the message is in every turn of the log. Checked on Docker: a `compose kill` counts as a stop asked for and is not restarted, which the demo relies on; an exit of the process itself, whatever its code, is.

## 10. Planning

**A job is split under a lease.** It stays in `planning` while a worker splits it, reserved by a lease on the job. A planner that dies lets it expire; completing or failing a plan applies only to a job still in planning, so two overlapping planners cannot double the chunks, and a job cancelled mid-split stays cancelled — the cancellation clears the planning lease itself.

**A refused plan fails the job, not the worker.** A kind that plans a chunk the schema refuses — an empty one, a payload that does not serialise — gets its job marked `error` with the reason.

**A dataset busy at planning postpones the job; it does not fail it.** Planning reads the dataset, and `prepare` may write to it, under the worker's write lock of that dataset (§12). The dataset's own lock never waits: when another process holds it — a person's save, another worker's chunk, an import — `DatasetBusyError` is raised, which says nothing about the job; so is its subclass `DatasetReplacedError`, which planning again also answers, since it reopens the dataset. The job stays in `planning`, with no error, its planning lease cut to `PLANNING_RETRY_DELAY`, two seconds, and any worker plans it again once that lease has expired, at the next turn of its loop — within about five seconds when it is idle. Planning again is safe, since `prepare` is idempotent. A log line records it, no event, and nothing bounds the retries: a job submitted during a long import waits in `planning` until the import ends or the job is cancelled. Any other planning failure still fails the job. Failed instead, the job would read "Dataset is being modified; retry when the current operation finishes", and the person would have to submit it again.

**This worker's own writes postpone a planning too, past ten seconds.** Planning waits for the worker's write lock of the dataset at most `PLANNING_WRITE_LOCK_WAIT_S`, ten seconds, then raises `DatasetBusyError` and takes the postponement above. The loop waits for a planning within its turn — no claim and no recovery of expired leases meanwhile —, so the wait is short. Ten seconds outlast a chunk's write for each of the four chunks in flight by default, and a compaction (§12). Without a bound, a chunk whose write hung — timed out, its thread abandoned with the lock held — would stop the next planning of that dataset inside the loop's turn for good, while the planning lease and the healthcheck stayed fresh, so nothing would report it.

**A planning has a time limit; past it, the job fails.** The split and the preparation together get `PLANNING_TIMEOUT_S`, ten minutes, a ceiling rather than an estimate, set far above that work, so that only a planning stuck in its reads or in `prepare` — storage that stopped answering, a kind's bug — reaches it and gives the loop's turn back. The job fails with "planning exceeded its time limit" rather than being postponed: planned again, it would hold the loop's turn for the whole limit each time, with no bound on the tries, and leave one more thread stuck each time. A `prepare` that had not started when the loop gave up never starts — it is checked under the write lock —; one already running holds the dataset's write lock, so a job submitted again waits for it. A time-out the planning meets itself, a socket's, is its failure, not the limit.

**An embeddings job with another model is refused at planning**, before inference runs (§12).

## 11. Events and the stream

**State events are written by the transaction that changes the state.** Identifiers are handed out before commit, so events from different connections can become visible out of identifier order. Counters survive it, being absolute; a state event has no later event to repair it. `running` and `progress` are written by the chunk's finishing transaction, under the job row's lock, and `done` by the settling one: a job's state events carry identifiers in their logical order whatever the concurrency.

**The stream drops duplicates by identifier, never by order**, within a window of a hundred identifiers, and a catch-up reads back a hundred identifiers before the client's last.

**The application announces its one state change.** A cancellation records a state event in its transaction, carrying the job's state after it and the request flag, so every open panel shows "cancelling" — not only the tab that clicked.

**The stream of all jobs has no catch-up.** Resuming from `Last-Event-ID` exists for the stream of one job only. The panel reloads its list when its stream reconnects, and shares concurrent reloads; a subscriber that falls behind has its stream closed so that it reconnects, instead of silently missing events. Validated in review.

**A malformed job identifier is an unknown job**, answered 404 on every route, the stream included.

**Job identifiers stay `uuid`**, unlike the shortuuid text of the rest of Pixano: the database guarantees uniqueness unprompted. Validated in review.

**A job reads `running` as soon as its first chunk is claimed.** The claim itself never joins `jobs`; a second query, run once the claimed chunks' tasks are launched, moves their jobs from `pending` to `running` under each row's lock, in identifier order, and writes the state event in the same transaction. The transition on the first finished chunk remains as the net for an outage between the two. A first version only turned `running` at the first finished chunk, so a first chunk of five minutes showed `pending` for five minutes.

## 12. Writes into LanceDB

**Identifiers are derived from the work** — the kind, the model, the key and the rank — so a replayed chunk replaces its rows instead of adding to them, and another model's rows for the same key are left alone. An identifier is a prefix shared by everything a key produced, then the rank: a replay finds every row of a previous run by prefix and deletes exactly those beyond what it wrote. A first version probed 32 ranks ahead, and a detection that shrank by more left ghost rows; the replacement is now exact, scoped by (kind, model, key) — not by (job, item): the job is the wrong scope, since a rerun must replace the previous run's rows. An embedding's identifier is a digest of the kind and its medium, without the model, since the table holds one (below): a rerun overwrites a medium's vector. Vectors written one per record, under the identifiers of an earlier version, are not overwritten: they stay beside the per-medium ones.

**Writes to one dataset are serialised** inside a worker, under one lock per dataset: a chunk's `write`, and a job's `prepare` at planning. Processing still overlaps. Outside that lock, a `prepare` that writes, planned while another job's chunk wrote the same dataset, would meet the dataset's own lock, which never waits, and fail — or fail that chunk, for good. Across processes — another worker, the application's saves — nothing serialises them, and the dataset's lock refuses whichever comes second: a person's save then gets a 409, a chunk fails (§8.1), a planning is postponed (§10). Serialising them across processes is step 4's.

**Every wait for that lock is bounded.** The lock is a thread lock at module level, so renewing the thread pool (§9) cannot release it: a write that never returns — storage that stopped answering — holds it until the process ends. A planning waits ten seconds for it, then is postponed (§10); a chunk waits five minutes (`CHUNK_WRITE_LOCK_WAIT_S`), then is handed back as transient, spending one of its attempts. Five minutes outlast the writes queued ahead of a chunk, and stay far below the chunk's half-hour time limit: a chunk behind a write that hangs is handed back, its thread freed, rather than waiting that limit out five times. Such a write still holds up every later write of its dataset in this worker until the worker restarts, and each chunk that waits for it does so in one of the worker's slots (§18).

**An embeddings table holds one model.** A job with another model or dimension is refused — at planning, and again at write time. Replacing a table's vectors on request (`replace_existing_embeddings`) is accepted for step 2, under conditions: the drop happens once, under the planning lease; a partly refilled table says so; the form asks for confirmation through a generic schema marker. It relies on the `prepare` hook of the kind contract: run once per job under the planning lease and the worker's write lock of the dataset, after the split and before the chunks are recorded, never for a replayed chunk or a job retried with its chunks; a no-op by default, idempotent, and never destructive without an explicit parameter — the contract suite checks the first two.

**The writer rereads a dataset before creating its embeddings table**, since creating overwrites: with two workers, the second's cached dataset would have erased the first's vectors. Two simultaneous creations remain for the writer role of step 4.

**Written tables are compacted** every 64 writes, old versions cleaned after an hour. A write creates a Lance version; a job of 50 000 images would leave 6 250 of them. The hour is what protects a reader holding an older version. Compaction runs under the dataset's write lock, in the chunk that triggers it. Measured (`scripts/measure_compaction.py`) on a classification table filled by chunk-sized writes: 0.12 s median at 10 000 rows, 0.30 s at 30 000 with a 0.9 s maximum, growing with the table. Acceptable for step 1; the policy — every N writes, at the end of a job, or owned by a writer role — was settled for step 2: it stays as it is until a compaction outlasts a chunk, then moves out of the write lock (§19).

**A search through a vector index re-ranks what it finds.** An index stores its vectors quantised, so it ranks its candidates only roughly: `Dataset.search_records` asks it for ten times the candidates it needs and ranks them on their full vectors (`Dataset._SEARCH_REFINE_FACTOR`); without an index the search is exact already, and LanceDB ignores the setting. Measured (`packages/pixano-worker/scripts/measure_vector_index.py`) on synthetic unit vectors of 512 dimensions gathered around a thousand directions, fifty searches of fifty records each, on an M1 Pro (8 cores, 16 GB):

| vectors | search | index build | median search | exact nearest records found |
| ------: | ------ | ----------: | ------------: | --------------------------: |
| 50 000 | exact, no index | — | 25 ms | 100% |
| 50 000 | IVF_PQ | 17 s | 2.0 ms | 90.2% |
| 50 000 | IVF_PQ, re-ranked | 17 s | 6.6 ms | 97.2% |
| 50 000 | IVF_SQ | 0.3 s | 2.2 ms | 99.7% |
| 50 000 | IVF_SQ, re-ranked | 0.3 s | 6.6 ms | 100% |
| 50 000 | IVF_HNSW_SQ, re-ranked | 14 s | 9.7 ms | 100% |
| 100 000 | exact, no index | — | 61 ms | 100% |
| 100 000 | IVF_PQ | 28 s | 2.6 ms | 61% |
| 100 000 | IVF_PQ, re-ranked | 28 s | 8.1 ms | 100% |
| 100 000 | IVF_SQ | 2.2 s | 2.9 ms | 98.7% |
| 100 000 | IVF_SQ, re-ranked | 2.2 s | 7.8 ms | 100% |
| 100 000 | IVF_HNSW_SQ, re-ranked | 35 s | 13.5 ms | 100% |
| 300 000 | exact, no index | — | 162 ms | 100% |
| 300 000 | IVF_PQ | 28 s | 3.2 ms | 32% |
| 300 000 | IVF_PQ, re-ranked | 28 s | 10.5 ms | 99.9% |

| 300 000 | IVF_HNSW_SQ, re-ranked | 89 s | 16.7 ms | 100% |

Re-ranked, `IVF_SQ` and `IVF_HNSW_SQ` find 99.9% to 100% of the exact nearest records, and `IVF_PQ` 97% to 100%, for 4 to 7 ms more through `IVF_SQ` or `IVF_PQ`. Re-ranking is what an `IVF_PQ` index needed most: read without it, the one the application's in-process computation builds (`build_record_embedding_index`) found a third to nine tenths of them. An index's training is random, so two builds of one table give equivalent indexes, not the same: the figures move by a fraction of a point from one build to the next.

**The embeddings job indexes its vectors at the end**, in its `finalize` (§8.5): an index is trained on the whole table, which no chunk sees, and built chunk by chunk it would be trained again at every write. The final chunk compacts the table, builds the `record_id` index — a search restricted to some records, and the lookup of a record's vectors for "similar to", filter on it —, then, from 50 000 vectors (`VECTOR_INDEX_MIN_ROWS`), the vector index the table's descriptor declares. Below 50 000 vectors an exact search takes 25 ms, and an index would only lose results. The line sits at half LanceDB's own threshold for an index because a "similar to" runs one search per medium of the record — six on a nuScenes record —, which must stay well inside the API's 500 ms p99 target: six exact searches take 150 ms at 50 000 vectors, 370 ms at 100 000. Past it the exact search grows with the table, while an index answered in under 11 ms at every size measured. A table the worker creates declares `IVF_SQ`, which trains ten times faster than `IVF_PQ` and, re-ranked, finds as much; a table created before declares `IVF_PQ`, `Dataset.create_record_embedding_table`'s default, and keeps it until the table is dropped and a worker creates it anew. Its training holds the worker's write lock of the dataset for 17 to 28 s at the sizes measured, while this worker's chunks of other jobs on that dataset wait for it — five minutes at most, `CHUNK_WRITE_LOCK_WAIT_S`, above. Every index is rebuilt whole, never extended, so a final chunk run again leaves the table as one run does. It does not take the dataset's own lock, as compaction does not: building an index changes no row, Lance commits it as a version of its own, and a person's save is never refused for its sake. A commit that conflicts with another writer of the table — the application's computation, a recompute, a rollback, another worker — fails the build: the final chunk is handed back to try again later, and meanwhile the search reads the previous index, if the table had one, or the table itself.

**Provenance.** Rows written through `writer.provenance()` carry the kind as `source_name`, and in `source_metadata` a self-contained provenance: the job identifier, the kind, the model and its version when the kind runs one, and the job's parameters minus the engine's (§19). Jobs are cleaned by truncation, so that identifier outlives its row: it is kept as an opaque run label, not a reference. Embeddings rows carry none: the model lives in the dataset's sidecar.

## 13. Media

**Paths are preferred, bytes are the fallback.** A view stored inside the dataset (`embed`, the default import mode) is sent as a data URI. A path outside the declared root was meant to be sent the same way, but the bytes are read from the dataset, which holds none for a view designated by path: such a medium is quarantined as not found (§18). This is the only route that serves existing datasets, and the demo runs on it; the plan's invariant — media do not travel through Pixano — is therefore exercised only by datasets imported by path. Accepted in review: nothing changes at step 1, and the cost of bytes over a real network is measured at step 4.

**A media path is normalised before the root check.** `/medias/../etc/passwd` passed it.

**One embedding per medium, media types chosen by the user.** A record may hold several media — a nuScenes record has six camera images and a point cloud. A job's parameters name the media types it covers (`image`, `video`, `point_cloud`, `text`, from `pixano.schemas.media_type_of`, where a video frame belongs to its video); a kind declares the types it can send to the inference, and a job choosing another is refused whole at planning, the types named — the user serves what they need or narrows the selection. A task is a medium: a chunk's cost is its number of inference calls, so batches of media stay alike where batches of records held six images or none, and a chunk never mixes tables. The payload is `{table, view_ids}`; a chunk queued by an earlier version, by record, fails saying so. A quarantined item is a medium, its record in the detail.

**Search is by medium, results by record.** A record's distance is its closest medium's; the search widens until it has k distinct records, and stops when it finds fewer vectors than it asked for. "Similar to" a record searches with every medium it has. The health counts distinct embedded media against the dataset's still images: `partial` means some image has no vector. Verified on nuScenes: 2 424 vectors, six per record for the 404 that have cameras, `ready`; "similar to" returns 20 distinct records for k = 20 in a quarter of a second.

## 14. Chunk size, measured

`chunk_size` is the only knob of the embeddings kind that changes how the engine behaves rather
than what it computes: it is at once the unit of work a retry must redo, the unit of progress a
user watches, and the size of the batch sent to the inference server. The default was 16 by
assumption. It is now 8 by measurement.

The measurement is a committed script,
[`packages/pixano-worker/scripts/measure_throughput.py`](../../packages/pixano-worker/scripts/measure_throughput.py),
so the numbers can be challenged by re-running them rather than by argument.

**The stack measured.** Docker with 8 CPUs and 8 GB, torch 2.14 CPU on aarch64, 8 threads, no
GPU; MobileCLIP2-S2 through `pixano-inference`; two datasets carrying the same 60 VOC images,
one with the bytes inline (~87 kB per image in `raw_bytes`), one referencing a path under the
declared media root.

| dataset         | media   | chunk | tasks | duration | tasks/s |
| --------------- | ------- | ----: | ----: | -------: | ------: |
| VOC 2007 Sample | inline  |     8 |    60 |   19.9 s |     3.0 |
| VOC 2007 Sample | inline  |    16 |    60 |   21.9 s |     2.7 |
| VOC 2007 Sample | inline  |    32 |    60 |   24.3 s |     2.5 |
| VOC 2007 Sample | inline  |    64 |    60 |   26.9 s |     2.2 |
| VOC 2007 (uri)  | by path |     8 |    60 |   19.1 s |     3.1 |
| VOC 2007 (uri)  | by path |    16 |    60 |   21.5 s |     2.8 |
| VOC 2007 (uri)  | by path |    32 |    60 |   26.4 s |     2.3 |
| VOC 2007 (uri)  | by path |    64 |    60 |   31.5 s |     1.9 |

A partial replay of the extremes lands in the same place: chunk 8 measured four times gives
19.1, 19.8, 19.9 and 19.9 s; chunk 64 measured three times gives 26.9, 31.2 and 31.5 s. The
spread at 64 is wide, the ordering never varies.

**Bigger batches are slower, not faster.** This is the opposite of what batching is supposed to
buy, it is monotonic across four sizes, and it holds for both storage modes. **The mechanism is
not established** — the measurement times whole jobs, so it cannot say whether the cost sits in
the inference call, in preprocessing, or in the worker. Per-phase timing, added
after the review, settles where: on Demo shapes (400 images, concurrency 4) chunk 8 takes 100 s of
wall time for 365 s of inference calls, chunk 64 takes 165 s for 514 s of calls, and reading and
writing stay under 5 s in both. The cost of a bigger batch sits inside the inference call — the CPU
server, not the worker. The number remains a fact about this stack, not a law: on a GPU, where a
batch amortises a kernel launch, the ordering will probably reverse. That is what the parameter is
for. The kind logs one line per chunk with its three phases, and the measurement script sums them
per job from the worker's log.

**Carrying the bytes costs nothing measurable here — and that does not validate the
invariant.** The two modes are within noise of each other. It would be convenient to read this
as "carrying bytes is free", and it would be wrong: both containers sit on one machine, so the
inline mode's data URI never crosses a network and the path mode's file never leaves a local
bind mount. The comparison this table makes is between two local paths. The invariant the plan
states — that media should not transit through Pixano — is about a worker separated from its
media by a network, which this stack does not have. **It remains unmeasured**, and step 4 is
where it can honestly be measured.

**Hence the default of 8.** It is the fastest measured, and it is also the smallest retry unit
and the shortest exposure to the lease, so nothing pulls the other way at this scale. The
choice is cheap to revisit: it is one field with a measurement behind it.

**A task is a planned record, not a produced vector.** The rate column counts tasks, and a task
is a record the planner scheduled. The embeddings kind drops records with no usable image, so
the two numbers only coincide on a fully imaged dataset. Measured on nuScenes: 26 766 tasks
produce 404 vectors, the rest being lidar sweeps with no camera. This is why the script refuses
to run without an explicit `--datasets` — a throughput averaged over records that were skipped
measures nothing.

**One trap worth recording.** On macOS `time.monotonic()` does not advance while the host
sleeps, whereas PostgreSQL `now()` is wall clock. A job that slept mid-run shows 31.5 s by the
script and 54 minutes by its event timestamps. Neither clock is wrong; they answer different
questions. Durations here are awake time.

**`chunk_size` is two settings in one.** For this kind it is both the unit of work — what a retry redoes, what the progress bar counts — and the size of the batch sent to the inference. They are separate questions: a GPU wants large batches, a retry wants small units. Noted in review and not split yet; a kind that needs both will declare a `batch_size` of its own.

## 16. Deployment

**The compose supposes no colocation.** Every link between components is an address in `.env`; the same files run against a remote database or a shared inference.

**Docker must not be the only way to run this.** Decided in review: a user who starts PostgreSQL, Pixano, the worker and an inference by hand must get the same behaviour. `docs/running-by-hand.md` runs the four components as plain processes with the same variables. What used to assume the compose is gone: the demo script takes the worker's media root as an option, the runner has no fallback media root, the schema-refusal message gives the `psql` command first, and `PIXANO_WORKER_ID` names a worker whose pid changes on every restart — the identity is what lets a restarted worker take its own chunks back at once. Verified with the worker and the application started by hand against the compose's PostgreSQL and inference. What still assumes Docker is the lease derived from the file probe (§20).

**The demo's inference is upstream pixano-inference, unmodified.** The compose builds the image of its own Dockerfile, from a checkout at v0.7.1, the release Pixano's client requires, and chooses the plugins with that Dockerfile's build args: `MODEL_PACKAGES` installs the SAM 2.1 and open_clip packages of its tree, `EXTRA_PACKAGES` its YOLO detection example, with Ultralytics pinned to the version the image was verified with. Nothing of ours is added to the image. The models served on CPU are listed in `docker/inference/models.cpu.py`, in this repository, since which models a deployment serves is that deployment's own choice: MobileCLIP2-S2, YOLO26n, and SAM 2.1 tiny and small (`sam2.1-tiny`, `sam2.1-small`, in float32 and without compilation, the plugin's defaults being meant for a GPU), one replica each, reserving 2 + 2 + 2 + 2 = 8 CPUs: all the machine it was measured on gives Docker, since a SAM call costs about 7 s on two CPUs in the container, through the server (§18). The reservation is a count, not a pinning: the application, the worker and PostgreSQL run on the same CPUs. Every listed model must load for the server to start: a missing plugin refuses the whole list, and strict startup, the server's default, refuses a machine with fewer CPUs than the list reserves, CLIP included (§18). Run by hand, the same three plugins are installed from the checkout, and sam-2 from GitHub at the commit their Dockerfile pins (`docs/running-by-hand.md`). Both ways, the SAM weights come from huggingface.co on first start, cached under `HF_HOME` (`/data/hf`, on the inference's volume, in the container), not in the YOLO weights directory. YOLO26n runs on Ultralytics, AGPL-3.0, a choice for the local stack only: nothing in Pixano names it. No tracking model is listed, since the four already reserve all eight CPUs: tracking by detection, in the legacy video workspace, needs another server that serves one, or two more CPUs and the YOLO plugin's `YOLOByteTrackModel` added to the list.

**The demonstration kinds are opt-in** (`PIXANO_WORKER_DEMO_KINDS`), off in the compose unless `.env` turns them on, as `.env.example` does. `fake` and `label` write wherever they are told; they are not for a shared deployment.

**Deviations from the lots, accepted in review.** No versioned migrations (§5). The application records a request and the worker inserts the chunks, rather than both in the API's transaction (§3). The sharing test now runs on 1 000 chunks, as lot 2 asked. The call semaphore of lot 9 is the engine's concurrency. Bytes travel for embedded datasets (§13). Embeddings carry no per-row provenance (§12). `review_status` and exact deletes by (kind, model, key), deferred at step 1, were delivered in step 2 (§19).

## 18. Known defects

- **The worker caches open datasets between jobs.** Planning reopens a job's dataset outside the cache, so a dataset recreated underneath the worker is seen as it is by the next job; a chunk of a running job reads the copy its planning opened.
- **The API learns of a worker's writes at the end of the job only.** Its event broker drops the cached dataset when a job reaches a terminal state, whether or not a stream is open — reproduced on the stack before the fix: job done, table on disk, search reported absent until a restart. During a job, what the worker wrote is not yet visible to a search. A change to `info.json` — a field a worker gave the entities (`Dataset.ensure_entity_text_field`) — is the exception: the API compares its mtime on each request (`Dataset.is_stale`) and reopens the dataset. On a local dataset only: on S3 the check always answers that nothing changed (§20).
- **The worker's embeddings differ from the application's.** The in-process path of `src/pixano/api/embeddings.py`, kept for now, writes one vector per record — its first image — and builds an `IVF_PQ` index whatever the table's size; the worker writes one per medium and indexes them at the end of its job, from 50 000 vectors (§12). On a multi-camera dataset the legacy explorer's "Update embeddings" never completes the table, which the health rightly reports as partial: embedding every image takes the embeddings job. Rows it wrote, like the rows a worker of step 1 wrote per record, are not replaced by a worker rerun; they stay beside the per-medium ones (§19).
- **The inference answers 500 for a client error.** A corrupt image or a missing path should be a 4xx. The worker works around it by isolating the culprit (§8.2); the fix belongs in pixano-inference. Issue texts are to be drafted; nothing is published without the architect.
- **Listing jobs costs three correlated subqueries per row.** Measured by the independent review at 256 000 chunks: 168–281 ms for fifty jobs, under the 500 ms p99 the project targets but with little margin at the cap of two hundred. Materialising the counters at chunk completion, or a covering index on `(job_id, state)`, are the two levers.
- **Compaction runs under the dataset's write lock** (§12).
- **A SAM 2.1 call takes about 7 s per image in the container, whatever its boxes.** Measured by hand on macOS on 2026-10-07, on an M1 Pro (8 cores, 16 GB) under other load: SAM 2.1 takes 1.0 to 1.2 s per image on two threads, 1.6 to 2.0 s on one, the small checkpoint 10 to 20 % slower than the tiny one. The image encoder dominates, so the boxes barely count: the slowest call measured, twenty boxes on one thread, took about 4 s. Checked again on 2026-10-08 from the entries of `models.cpu.py`, by hand: 1.9 s (tiny) and 2.1 s (small) for one box on a 500 × 375 image. Inside the compose's inference container, on the same machine (Docker Desktop, arm64, 8 CPUs), a call costs five to six times more, measured on 2026-10-09: tiny, three boxes on a 224 × 224 image, takes 10.7 s on one thread, about 6 s on two and 3.7 s on four; through the server with one CPU per replica, 13 s for tiny and 14 s for small. A replica answers one call at a time, and the server's 60 s limit on a segmentation call counts its time in the queue: at one CPU each, as the compose first served them, the last of four calls in flight — a worker's default concurrency — came back after 52 s on tiny and 59 s on small, and any further call — the smart-segment tool, a second worker — was answered 504. Hence two CPUs per SAM model (`SAM_CPUS`), all eight of the measuring machine's for the four models (§16). The 6 s was measured with torch's threads inside the container; through the server on two CPUs, a run of the whole stack (2026-10-09) measured about 7 s per image for tiny and 7.8 s for small, so a queued call waits about 4 × 7.8 s ≈ 31 s at most, its own included. With fewer than eight CPUs the inference does not start, CLIP included, unless run with `--no-strict-startup`, which places the models in list order and leaves `sam2.1-small` out on six or seven. Each replica holds about 1.5 GiB, 2 GiB at peak. Every client shares the two replicas, so four calls queued ahead delay the interactive smart-segment tool by up to about 31 s in the container. 8 GB of Docker memory holds the whole stack: on pixano-inference v0.7.1, both SAM models having run (2026-10-19), `docker stats` read about 5.8 GiB of the 7.75 GiB given to Docker, 5.12 of them for the inference and its four models; on v0.6.0, on 2026-10-09, 5.5 and 4.85. **Not verified yet**: whether the inference's healthcheck allows a first start that also downloads about 340 MB of SAM weights.
- **The stream of one job replays its whole history on first connection.** 6 250 events for a job of 50 000 images. Acceptable today; a bound or a `since` parameter is the obvious fix, and it is a choice about what a fresh client sees.
- **The pool checks each connection before lending it** (`SELECT 1` per borrow). Negligible today; to measure at step 4 if the claim rate ever matters.
- **A write that never returns holds its dataset until the worker restarts.** A chunk's `write` stuck in storage that stopped answering keeps the worker's write lock of its dataset, which renewing the pool cannot release (§9). Every wait for it is bounded (§12), and no other dataset's write waits on that lock. But the jobs of that dataset are postponed at planning, and its chunks are handed back until set aside after their last attempt; each attempt first runs the chunk's work, its inference included, then waits five minutes in one of the worker's slots. A job with many chunks on that dataset can fill every slot for hours, so the other datasets' chunks are written late — not never — until the worker restarts or those chunks are set aside.
- **A path outside the declared media root is quarantined, not sent as bytes.** The resolver falls back to the dataset's bytes for it (`MediaResolver._inline`), and a view designated by path holds none: the medium is quarantined as "media not found". The worker does not read such a file itself either, since it reads only under its media root. Read in the code, not reproduced on a dataset; the test of that fallback uses a source that returns bytes for any view.
- **An entity's delete removes it whatever names it, unless asked not to.** `DELETE …/entities/{id}` deletes the entity even when an annotation, a child entity or a dynamic state still names it, and those rows are left naming nothing: the server neither cascades nor refuses. A client that cannot see every row naming the entity can ask for the rule: with `?only_if_unnamed=true`, the server deletes the entity only when no annotation of any table (its `entity_id`, a message's `entity_ids`, a relation's ends), no child entity and no dynamic state names it, under the dataset's write lock — on a local dataset; S3 has none —, and answers `{"deleted": true|false}`; 404 when there is no such entity (`BaseService.delete_if_unnamed`). Without the parameter, a delete is as before. The legacy interface's entity delete sends no `only_if_unnamed`: a row in a table its workspace did not load is left naming a deleted entity, as before.
- **A delete applies no review rule, by design; what it leaves behind can be wrong.** A delete is how a model's row is rejected (§19), so `BaseService.delete` removes a model's row whatever its status. Deleting what such a row names is not checked, though: a row naming a missing entity or tracklet is refused at every later update by the reference checks; an edit of the entity it names does not fail on it, since the acceptances the edit makes skip those checks (§19). The server neither cascades nor refuses; a rule on the server — refuse or cascade a delete that would leave a model's row naming nothing — is the only fix for every client.
- **An entity edit and the acceptances it makes are two writes.** LanceDB has no transaction across tables: the entity is stored first, then each table's acceptances in one write (§19). A failure of storage between the two leaves the entity changed and the model's rows naming it still pending, and a retry of the same request finds nothing to accept, since the entity no longer differs: the next run of the model then writes its own values back over the person's. The acceptances skip the per-row reference checks — a change of status cannot break a reference — so a reference left dangling on one of the rows does not fail them after the entity was stored; what is left is a failure of storage itself.

## 19. Decided for step 2

Questions raised by step 1's review, and the rules step 2 settles for them; each rule is stated here once the code that applies it lands. [`OPEN_QUESTIONS.md`](../OPEN_QUESTIONS.md) records the questions step 2 leaves open, each with its alternatives and the code that holds it.

- **Embeddings are per medium, not per record.** One vector per image view composing a record, `view_id` filled; a search finds a medium and returns its record. Returning media is left open. The application's in-process path stays for now. Vectors written one per record — by that path, or by a worker of step 1 — stay beside the per-medium ones until a job runs with `replace_existing_embeddings` (§12; decided 2026-10-20), a parameter the embeddings job does not take yet.
- **Provenance** lives in `source_metadata`, set by the writer: `job_id`, `kind`, `model`, `model_version`, `params`. Dedicated columns when a filter by model becomes a need.
- **For annotations, another model adds; the same model replaces its own rows.** The replacement key is (kind, model, key) — the key a kind writes under, usually a record —, and `replace` is exact by that key (§12). Both halves are decided (2026-10-20): a rerun of the same model replaces its own pending rows, and another model's rows add beside them. Cleaning duplicates across models may be a workflow later. An embeddings table, by contrast, holds one model (§12).
- **A rerun only replaces rows still `pending`.** Rows a person accepted are frozen for that kind: they keep their rank, and the rerun's rows take the ranks left free.
- **`review_status`** takes `pending` and `accepted`, on every entity annotation schema (dataset spec version 3; an older dataset gains the column, empty, when opened); empty for a human annotation, `pending` set by the writer for a model's. A model's row becomes `accepted` when a person accepts it, or saves an edit of it; it keeps `source_type = model`, the model's provenance and score. **Rejecting deletes the row**, with its entity when nothing else names it (decided 2026-10-20). Two consequences, accepted with that decision: a rejected proposal leaves no trace, so a rerun of the model may propose it again, pending; and the dataset no longer records how many proposals were rejected, or edited before being accepted — an edited and an untouched accepted row look the same, apart from what their provenance and score say. A model's row stored with no status — re-imported from JSONL, whose grammar carries none, or stored by the legacy smart tracking — reads as `pending`, from one definition, `pixano.schemas.NOT_REVIEWED_STATUSES` (`pending` and the empty status), read through `review_status_of` and `stored_statuses` — by these rules, by the queue and by the export by status — and by the worker's writer, where `is_reviewed` lets a rerun replace such a row.
- **A person saving an edit of a model's row accepts it** (decided 2026-10-20). The rules are the API's, in `src/pixano/api/review.py` and the service, and hold for every entity annotation, whatever its kind. A request that changes a model row's content stores it `accepted`, from `pending` or `accepted`: the person chose to save that annotation in the dataset, and left pending it would be replaced by the next run of the model, which is to replace pending rows only (`ReviewStatus`). Content is every field but the provenance, the score, the status and the server's timestamps, compared after validation, so a body that changes nothing, or an empty one, accepts nothing. A request carrying a change and `accepted` stores both. A status equal to the row's own is an echo, not a decision, and so is `pending`, which no person gives: a client that edits by sending back every field it read sends the status back too. The legacy interface did so for every resource; it no longer sends the status, which these rules would refuse on its second edit of a model's row stored with no status, and on the split of a model's tracklet, whose clone is a person's row. The row keeps `source_type = model`, the model's provenance **and its score**, whatever the client sent: the web interface sends its own source and a score of 1 with every edit, which erased the score of an edited box. The score is not one column name but each schema's own declaration, `MODEL_SCORE_FIELDS` (read through `pixano.schemas.model_score_fields`): `confidence` on a box and on a 3D box, `confidences` on a classification; no other entity annotation schema holds one, and a guard test fails on a score-like field left undeclared. **A list of scores follows what it scores**: a classification's `confidences[i]` scores its `labels[i]`, which the schema declares next to its score fields, in `MODEL_SCORE_ALIGNMENT` (`{"confidences": "labels"}`, read through `pixano.schemas.model_score_alignment`); the service applies it whatever the kind, and a guard test fails on a list of scores that does not say what it scores. When an edit of a model's row leaves the scored field as stored, the model's scores stay as stored, whatever the client sent. When it changes that field, the scores are realigned: each value the model gave keeps the model's score — a value given twice keeps both, in the model's order — and a value the person adds takes the score the client sent at its position, in a list aligned with the field, as the schema requires of any row; a value added without such a score is answered 400. Kept as stored while the labels changed, the scores would score other labels, or no longer match their number and fail validation: the web interface, which sends the object's label alone when it moves a classification to another object, would get a 400 for a model's multi-label one. A `PUT` whose body carries an `id` other than the path's is answered 400 before any of this, for every resource: the rules are checked on the row the path names, and the merged row would be written under the body's id, over another row.
- **A person's edit of an entity accepts the model's pending annotations that name it.** What an annotation says can live in its entity — a model's class, for instance, written on the object its box names —, and a person who fixes it there edits the entity and leaves the annotation as the model wrote it. That is a saved edit of what the annotation says, and follows its rule — a reading of it, still to confirm: an update of an entity that changes a field other than its identifier, record, parent and timestamps (`ENTITY_SYSTEM_FIELDS`) makes every model annotation naming it, in any table of entity annotations and whatever its kind, `accepted` when it is pending (or stored with no status), in the same request, under the same write lock (`review.acceptances_of_entity_edit`). Left pending, the annotation would be replaced by the next run of the model, which would write its own class back over the person's. A row already accepted is left as it is, not even rewritten. Two consequences follow. A fix of the object accepts rows nobody looked at: every pending row naming the object is accepted, whatever its kind — a mask a model drew on the object goes with its box, whatever its outline. And any change of the entity counts, not only its class: editing a VOC `is_difficult` flag in the legacy object inspector accepts the object's pending annotations, which a rerun then leaves as they are. The entity is stored first, then each table's acceptances in one write that skips the per-row reference checks: an acceptance changes the status alone, so it cannot break a reference, and the checks cost lookups per row and per reference — relabelling an object named by 500 masks and a tracklet took 3.4 s at the median, 52 ms without them — and would fail the whole request on a reference some other edit had left dangling on one of the rows. LanceDB has no transaction across tables, so the two writes are not atomic (§18). An echo of the entity, or a change of its parent only, accepts nothing. Only an update of the entity row does, for now: an edit of its dynamic state (a per-frame attribute) accepts nothing, and neither does a delete of the entity. A table without the status column — a dataset whose migration to the review layout failed, a read-only library — is skipped: no decision can be stored in it.
  - **The legacy interface has no Accept.** At default settings, a model's row becomes accepted there in two ways: a person saves an edit of the row, or edits the object it names in the object inspector. Its gestures that move a model's rows to another track or object — the timeline's glue, the Fusion tool, a relink — save each row they move, which the saved-edit rule above stores `accepted`, though nobody looked at it frame by frame. Like the entity edit, a reading of the saved-edit rule, still to confirm.
- **One decision: `accepted`, from `pending`.** Accepting takes a pending row; `accepted` asked of an accepted row is an echo. Rejecting is no status: it is a delete (`DELETE …?prune_orphan_entity=true`), which applies no review rule (§18). No update sets `pending` or takes a row back from `accepted`; a create of a model's row may still carry `pending`, `accepted` or no status — the legacy smart tracking and interactive segmentation store theirs with none. The empty status and any other value on a model's row are answered 400. A person's row takes no status: a non-empty one is refused with a 400, on update and on create, while a model's row may still be created with one. Two exact echoes pass that these rules would otherwise refuse: a person's row stored with a status before them, and a model's row stored without one.
- **The next record to review is found by the server, whatever the kind.** `GET /datasets/{id}/review/next?status=pending&after=<record_id>` answers `{record_id, remaining}`: the first record after `after`, in record-id order rather than the explorer's, that holds a model's annotation at that status, wrapping round to the first; `null` when no record does. `status` is `pending`, the default, or `accepted`; any other value is answered 422. `remaining` counts those records, the one being left included while it still holds one. It scans every table of a kind a person can review, reading record ids only — and view ids, on a dataset holding a view no interface shows (below) — and never resolves a table through the service, which would create a missing one. The reviewable kinds are one predicate, `pixano.schemas.is_reviewable_annotation`, which the export by status reads too: every entity annotation but tracklets — structure, the span of an object across frames, reviewed through the per-frame annotations it groups — and relations and text spans, which no interface can review yet. A model's row of such a kind would keep its record in the queue for good; a kind leaves that list once an interface can review it. So would a row drawn on a view no interface can show for review — a video or its frames, a frame of a point-cloud sequence, a PDF: the review interface has widgets for still images, point clouds and texts only. The views shown are one predicate too, `pixano.schemas.is_reviewable_view`, read by the queue alone. A row whose `view_id` names any other view, by its id or by its logical name, is left out of the queue and keeps its status, and a record holding nothing else is not proposed; a row with no view, or naming none the dataset holds, stays. **The rows the legacy interface's video tools store are such rows**: SAM2 video tracking's masks and tracking by detection's boxes, a model's output stored without a status. A person kept them, but they are not marked accepted — by decision, a model's output is accepted by a person reviewing it — so they stay pending, unless a person edits one in the legacy workspace, or moves it to another track or object there (the legacy interface's gestures, above), which stores it accepted; no interface can review them yet, and an export of accepted rows leaves out those still pending. On a dataset holding such a view, the view ids found are looked up in its tables, by one filter up to a thousand ids, else by reading the table's ids whole: in process on an M1 Pro, 100 000 rows under review on 300 000 frames take about 105 ms, and reading a million frame ids about 160 ms. A dataset without one reads no view id. A table without the status column — a dataset whose migration to the review layout failed, a read-only library — is skipped as well: no decision could be stored in it. Measured against the 500 ms p99 target: 11 ms at most, in process, on nuScenes (26 766 records, no annotation yet); on a synthetic dataset of the same size holding 107 064 boxes and 26 766 masks, through HTTP, a p99 of 70 ms when written in large batches, and of 222 to 313 ms when written in batches of a hundred and never compacted (1 072 and 269 table versions). The cost follows the number of table versions: the worker compacts what it writes (§12), the API does not compact what people save, and `pixano data optimize` compacts a whole dataset.
- **An export can keep only the model annotations of chosen statuses**: `review_statuses` in `POST /io/exports`, `--review-status` on the command line, and `ExportSpec.review_statuses`, which `export_dataset` takes. Every annotation no model produced is kept, and only the reviewable kinds are filtered: relations and text spans are kept whatever their status — kept by the reader, `RecordBundleReader`; no export format writes a relation (`pixano_jsonl` reserves the kind, `coco` has none), so an entity a kept relation protects is exported with no annotation by `pixano_jsonl`, and is absent from `coco`, whose entries come from boxes, masks and keypoints. Tracklets are never filtered by their status. A tracklet no model produced keeps its entity, like every annotation no model produced. A model's tracklet is structure: it goes with its entity, like the entity's dynamic states, and does not keep it. A kept relation naming a tracklet keeps that tracklet's entity, and so the tracklet: otherwise a person's tracklet would go with an entity the selection emptied, and a relation could be left naming a tracklet dropped. See the amendment of 2026-10-05 in [the import/export spec](./data-import-export.md).
- **An import can queue the embeddings of the dataset it imported into** (step 2's second version, decided 2026-11-02). Whoever starts the import asks for the embeddings job — naming a model is asking —, or the deployment's default does: `PIXANO_EMBEDDINGS_AFTER_IMPORT`, true, which only applies where the job can run — a queue reachable where a worker declared the job, and a model, `PIXANO_EMBEDDINGS_MODEL` or else the first embeddings model the application's inference serves — and not to an import whose plan holds no still image. The import queues the job once its data is in, at most once, says on its own job what became of it, and stays done whatever the outcome; a cancel that came too late to stop the import queues nothing. The request is kept with the import job, so that a resumed import still queues it. An add import has the job compute the whole dataset again, with the model its embeddings already use: the job has no way to compute only what is missing. The application queues it as it queues any job: the import never waits for the worker. Details in [the import/export spec](./data-import-export.md), amendment of 2026-11-02.
- **Compaction** stays as it is until a compaction outlasts a chunk; then it moves out of the write lock. Measure at 500 k rows once a kind produces that volume.
- **Chunks are unchanged.** Video tracking is on hold; when it comes, a chunk is a video, with an internal progress and a weight per chunk deciding its time limit.
- Deferred to a second version of the step: NER, statistics and partial writes, clustering, video. Vector indexing, deferred with them, is delivered through a job's closing step (§8.5, §12).

## 20. What steps 3 and 4 open

Step 3 brings several sources of media and datasets, object storage among them; step 4, workers on other machines. The limits below are what each will meet in what step 2 left.

### 20.1 Step 3

- **A medium designated by URL is not diagnosed.** When the inference refuses every medium of a chunk, the media designated by URL go to quarantine with the rest (§8.2), although the inference may only fail to reach the source — a host missing from its allowlist, a presigned URL expired. Each source of media is to say, beside its own designation, what to check when the inference refuses it, and whether the chunk is worth retrying, as the resolver says it for paths (`MediaResolver.path_refusal_diagnostic`): a new source then adds its own case without touching the kinds' shared code.

- **A remote dataset has no lock and no staleness check.** On S3, `Dataset.write_lock` and `dataset_mutation_lock` do nothing, and `Dataset.is_stale` always answers false. So what relies on the lock is a check followed by a write there — the conditional delete (`only_if_unnamed`), the orphan prune, the acceptances of an entity edit (§19) —, and the API keeps serving the entity schema it first read until a job ends (§18). Nothing breaks in step 2: the worker opens a local library only, so no job writes an S3 dataset. Step 3's sources would, and the worker's writes with them — a field added to the entities among them. On a local disk, the staleness token is the mtime of `info.json`, which attribute caching or coarse timestamps can hide on a network filesystem. Step 3 needs a token that holds everywhere — the manifest's version or ETag, or a counter the one writer of `info.json` increments — and must refuse, or flag, the writes made of several steps on a source with no lock.

### 20.2 Step 4

- **Does a remote worker reach PostgreSQL directly, or go through the API?** The opening question of the step: everything below depends on it.
- **A cap on calls per model** is impossible with today's claim: `job_chunks` carries neither kind nor model, by choice. It needs both denormalised on the chunk and the partial index revisited.
- **`job_kinds` has no liveness.** A dead worker leaves its kinds on offer, and a job submitted with no worker waits without limit. A live worker claims planning for kinds it does not know, and fails the job. A per-worker heartbeat in the database, and a planning claim restricted to the kinds a worker declares.
- **Writes are serialised per process.** Two simultaneous creations of an embeddings table, and two workers compacting one table — a Lance commit conflict, logged, no loss, to measure.
- **The lease derives from the docker probe** (`LEASE_TTL = max(120, 4 × MAX_HEARTBEAT_AGE_S)`), and the file probe means nothing off Docker.
- **The per-chunk lease** refreshes one row per chunk in flight; worth revisiting if workers number in the dozens (§6).
- **The cost of bytes over a network** (§13).
- **Planning has no fencing token.** The planning lease records no claimant, and the statements that refresh, finish or fail a planning, or postpone it, check only that the job is still in `planning`. With two workers, a planner whose lease lapsed — a PostgreSQL restart ends its refreshes for good, a slow inference holds it — can extend or cut the lease of the planner that took the job over, fail its job, or run a destructive `prepare` after that planner's chunks have written, deleting rows that are never written again. The time limit of §10 stops a `prepare` its own worker gave up on, not another worker's. A token — the claimant and a counter — recorded at the claim, checked by each of these statements and again right before `prepare`, closes it (`SCHEMA_VERSION` bumped).
- **A dataset's layout is migrated whenever it is opened** — by the library listing, the command line, the API or the worker —, and a migration that fails leaves the dataset open at its old layout. With the application and workers on different builds, migrating is to become an explicit action, or the writer role's, and how a migration derives the values it backfills — literals today, repeating the schemas' defaults — is decided with it.

## 21. Open questions

- **Fairness across jobs.** The claim orders by chunk identifier, so an older job drains before a newer one and a large job can starve a small one. Batching by job would give locality at the cost of arbitrary job order.
